# Speed Limit Neighbourhood Dynamic Segmentation

## Purpose

Produce a separate segmented representation of the LRS network that combines three event tables:

| Event table | Key field(s) contributed |
|---|---|
| `SDEADM.E_StreetClass` | `ST_CLASS` → aliased as `STR_CLASS` |
| `SDEADM.E_SpeedLimit` | `SPEED` (domain `TRN_speed_value`, Short) |
| `SDEADM.E_SpeedLimit_Neighborhood` | `REVIEW_STAT` (domain `TRN_speed_status`), `DATE_EFFECTIVE` |

The output supports the **SpeedLimit_Neighborhood_VW** layer shown in the data model diagram.

### Output schema (`SpeedLimit_Neighborhood_VW`)

| Field | Source | Notes |
|---|---|---|
| `ROUTE_ID` | overlay `ROUTEID` | FK → `LRSN_Route` |
| `STR_NAME` | network field `STR_NAME` | |
| `FULL_NAME` | network field `ROUTENAME` | |
| `STR_CLASS` | `E_StreetClass.ST_CLASS` | domain `E_StreetClass` |
| `SPEED` | `E_SpeedLimit.SPEED` | domain `TRN_speed_value` |
| `REVIEW_STAT` | `E_SpeedLimit_Neighborhood.REVIEW_STAT` | domain `TRN_speed_status`, length 255 |
| `DATE_EFFECTIVE` | `E_SpeedLimit_Neighborhood.DATE_EFFECTIVE` | Date |
| `SHAPE` | geometry from `OverlayEvents` | Polyline M, MTM5 |

---

## Should `E_SpeedLimit` and `E_SpeedLimit_Neighbourhood` be added to `self.event_tables`?

**No.** `self.event_tables` is the event list consumed by `update_dynamic_segmentation()`, which
builds `TRNLRS_segmented_street_events` — the intermediate feature that feeds
`TRNLRS_TRN_street_VW`, `TRNLRS_TRN_street_retired`, and `TRNLRS_TRN_street_lanes`.

The speed-limit neighbourhood output is generated by a dedicated list
`self.speed_limit_neighbourhood_event_tables` (three tables only) and written to
`TRNLRS_segmented_speed_limit_events`. Keeping the two overlays separate means:

- The main street-view segmentation grain and schema are not changed.
- Speed-limit boundaries, which do not align with address-range or ownership boundaries,
  cannot introduce spurious short segments or duplicate FDMIDs into the primary QA checks.
- The speed-limit view can be refreshed independently on a different schedule.

---

## Impact on `TRNLRS_trn_street_vw` if the events were added to `self.event_tables`

`arcpy.locref.OverlayEvents` splits geometry at every event boundary from every input table.
Speed-limit and neighbourhood-review records can start and end at points that do not coincide
with address-range or street-class boundaries. Adding them to the main overlay would:

- Increase the row count in `TRNLRS_segmented_street_events` and therefore in
  `TRNLRS_TRN_street_VW`.
- Potentially produce new duplicate `FDMID` values (the same underlying street segment split
  into sub-segments at speed-limit boundaries, each inheriting the same `FDMID`).
- Potentially produce new short segments that fail the < 3.174511 m QA check.
- Require the main street-view SQL to explicitly handle `SPEED`, `REVIEW_STAT`, and
  `DATE_EFFECTIVE`; without that, the fields exist only in the intermediate feature.
- Affect downstream consumers (NSCAF, locators, lane data) that expect the existing
  segmentation contract.

Do not add these events to `self.event_tables` unless the business requirement is to
permanently change the segmentation rules for the primary street view.

---

## Pipeline

```
LRSN_Route + E_StreetClass + E_SpeedLimit + E_SpeedLimit_Neighborhood
        │
        ▼  arcpy.locref.OverlayEvents
TRNLRS_segmented_speed_limit_events   (RW SDE, PUBLIC view granted)
        │
        ▼  SQL query layer (TO_DATE IS NULL)
SpeedLimit_Neighborhood_VW            (RW SDE → truncate/append)
        │
        ▼  append_feature()
SpeedLimit_Neighborhood_VW            (RO SDE — kept in sync manually)
```

## Implementation in `LRS_updates.py`

### Constants

```python
SDE_SPEED_LIMIT_SEGMENTED_FEATURE_NAME = "TRNLRS_segmented_speed_limit_events"
SPEED_LIMIT_NEIGHBOURHOOD_FEATURE_NAME = "SpeedLimit_Neighbourhood_VW"
```

### `DynSegFeature` attributes

```python
self.speed_limit_neighbourhood_event_tables = [
    rf'{self.sde_workspace}\SDEADM.TRNLRS\SDEADM.E_StreetClass',
    rf'{self.sde_workspace}\SDEADM.TRNLRS\SDEADM.E_SpeedLimit',
    rf'{self.sde_workspace}\SDEADM.TRNLRS\SDEADM.E_SpeedLimit_Neighborhood',
]
```

### Key methods

| Method | What it does |
|---|---|
| `update_speed_limit_neighbourhood_segmentation()` | Runs `OverlayEvents` against `LRSN_Route` using `speed_limit_neighbourhood_event_tables`; writes `TRNLRS_segmented_speed_limit_events`; grants PUBLIC view. |
| `update_speed_limit_neighbourhood(out_feature, segmented_feature_name)` | Builds a query layer from the segmented feature (`TO_DATE IS NULL`), maps overlay fields to the target schema, calls `append_feature()` to truncate and reload `SpeedLimit_Neighbourhood_VW`. |

### Spelling variant

If the target SDE uses Canadian spelling, pass the alternate name:

```python
dyn_seg.update_speed_limit_neighbourhood_segmentation(
    neighbourhood_event_name="SDEADM.E_SpeedLimit_Neighbourhood"
)
```

### `__main__` block (added section)

The speed limit segmentation runs after the main street-view update, independently of whether
the main QA checks passed or failed:

```python
sde_speed_limit_rw = os.path.join(SDEADM_RW, f"SDEADM.{SPEED_LIMIT_NEIGHBOURHOOD_FEATURE_NAME}")
sde_speed_limit_ro = os.path.join(SDEADM_RO, f"SDEADM.{SPEED_LIMIT_NEIGHBOURHOOD_FEATURE_NAME}")

segmented_speed_limit = dyn_seg_feature_new.update_speed_limit_neighbourhood_segmentation()

if segmented_speed_limit:
    updated = dyn_seg_feature_new.update_speed_limit_neighbourhood(out_feature=sde_speed_limit_rw)
    if updated:
        append_feature(sde_speed_limit_rw, sde_speed_limit_ro, SDEADM_RO)
```

## Pre-run checklist

1. Confirm the event class spelling in SDE: `E_SpeedLimit_Neighborhood` (American) or
   `E_SpeedLimit_Neighbourhood` (Canadian). Pass the correct name to
   `update_speed_limit_neighbourhood_segmentation()` if using the Canadian form.
2. Confirm `E_StreetClass` exposes `ST_CLASS` — the query aliases it to `STR_CLASS`.
3. Confirm `E_SpeedLimit` exposes `SPEED` (Short, domain `TRN_speed_value`).
4. Confirm `E_SpeedLimit_Neighborhood` exposes `REVIEW_STAT` (Text, domain `TRN_speed_status`,
   length 255) and `DATE_EFFECTIVE` (Date).
5. Confirm the target publishable feature class `SDEADM.SpeedLimit_Neighbourhood_VW` exists in
   both the RW and RO connections with the expected schema.
6. Run in dev first and compare row counts and geometry lengths against the source event tables.
